# Specification

What the system does and why. How it does it lives in `PLAN.md`. Every rule here must respect `CONSTITUTION.md`.

## Client context

A family-owned food manufacturer grew fast. Financial data is spread across seven ERPs (some on-premise, some cloud) plus spreadsheets. Each business unit's finance team answers questions by running SQL and digging through its own ERP by hand. Simple questions ("which customers are spending more?") take days, and preparing a board deck consumes the team.

This lab simulates two of those systems:

- **Source A — ERPNext (cloud, REST API):** company "Harvest Table Foods", sales invoices for January to October 2026.
- **Source B — legacy export (on-premise, no API):** a CSV export of the same period from another business unit.

Rationale: One modern source with an API and one legacy export without one reflect the real spread in a mid-market company; two is the smallest number that proves the design, and seven ERPs would be the same design with more adapters behind the same interface.

## Problem

Revenue data lives in separate systems that don't agree on customer names or formats, and some of them contain errors. Nobody can see total revenue per customer across units, or whether it is going up or down, without days of manual work. Worse, when numbers are combined by hand, bad records slip into the totals and nobody notices.

Rationale: The problem has two halves, delay (manual consolidation) and trust (bad data entering unnoticed), and the system addresses both.

## Objective

Give the finance team one trusted view of revenue per customer across both units, updated within minutes, where every number can be traced back to the source documents and bad records are shown separately instead of being silently included.

Rationale: Three ideas carry the spec: trusted (fail-closed, quarantine, reconciliation), updated within minutes (automatic sync) and traced (every number leads back to its source documents); the goal is a number the CFO can put on a board deck without re-checking it.

## Users and access

- Users sign in with their Google account.
- Only team members on an allowlist can see data. Anyone else who signs in sees an access-denied page and no data.
- All members are **viewers**: they can browse, filter and chart everything, but nobody can create, edit or delete financial data through the app.
- Financial data changes only through the sync pipeline. Two kinds of fixes exist, and neither happens in the dashboard:
  - **Bad data** (wrong total, missing field, bad date) is fixed in the source system and synced again.
  - **Unknown customers** are fixed in the customer mapping, a versioned file in the repository changed only by commit (BR05).

Rationale: The dashboard is derived data and can be rebuilt from the sources; if people could edit it, it would drift from the ERPs and nobody would know which number is true, so data fixes happen at the source and the customer mapping is versioned config, reviewed like code.

## User stories

- **US01** — As a finance member, I want to see total revenue per month across both units, so I can answer "how are we doing?" without opening each ERP.
- **US02** — As a finance member, I want to filter revenue by source, customer and date range, so I can compare units and drill into one customer.
- **US03** — As a finance member, I want to see which customers are growing, declining, new or have stopped buying, so I can prepare the board deck and flag accounts at risk.
- **US04** — As a finance member, I want to see the records that were rejected and why, so I know what is missing from the totals and which source needs fixing.
- **US05** — As a finance member, I want to know how fresh each source is, so I know whether the numbers are current.
- **US06** — As a finance member, I want to see which source documents make up any number, so I can trust it and answer "where did this come from?".

Rationale: Taxes are deferred to Q1 because the seed data has none, and costs depend on purchase invoices (a planned extension); US04–US06 follow from the fail-closed and traceability principles.

## Delivery priority

- **P1 (must work first):** R01, R03, R04, R05, R06, R07, R09, R10, R13, R14, all business rules except the BR08 trend labels, and the acceptance criteria that test them.
- **P2 (build if P1 is done; otherwise explain the design):** R02 (webhooks), R08 trend labels, R11 (Google sign-in), R12 (drill-down), R16 (readability), R17 (responsiveness), R18 (loading feedback), R19 (source breakdown), R20 (financial clarity), R21 (trend visibility).

Rationale: P1 covers what makes the number trustworthy (fetch, normalize, validate, quarantine, idempotency, reconciliation); webhooks are the biggest time risk (public endpoint, ERPNext configuration, signatures) and only a latency improvement on top of a pipeline that is already correct.

## Functional requirements

- **R01 (P1)** — Fetch sales invoices from Source A incrementally, including submitted (docstatus 1) and cancelled (docstatus 2) ones. Each run asks only for invoices changed after the cursor saved by the last successful run. The cursor is the pair (last-modified timestamp, document name), and each run re-reads a 65-minute overlap window before the cursor.
  Rationale: The 65-minute overlap covers the repeated hour when daylight saving time ends and an invoice whose transaction commits slightly after its timestamp; cancelled invoices are fetched so cancellations don't depend on webhooks, which can be lost, and idempotency absorbs anything read twice.
- **R02 (P2)** — Accept change notifications pushed by Source A (webhooks). Requests without a valid signature are rejected. Accepted notifications are only queued; periodic fetching (R01) keeps running as the backstop, so notifications are never the only path.
- **R03 (P1)** — Ingest Source B export files. An operator uploads a file named `unit_b_export_YYYY-MM-DD.csv` (the export date) to a storage bucket; a scheduled job checks for new files every 5 minutes. The newest file is the complete state of Source B (BR10).
  Rationale: Uploading through the dashboard is out of scope, so files land in a Supabase Storage bucket read by a scheduled job, and nothing runs on a developer machine.
- **R04 (P1)** — Convert records from every source into one canonical invoice: source, source document ID, canonical customer, invoice date, currency, lines, net total, and whether it is a credit note. The invoice date is the posting date (Source A `posting_date`, Source B `INV_DATE`), never the creation or modification date.
  Rationale: An invoice for March can be created in April (backdated posting) and must count in March.
- **R05 (P1)** — Resolve each source customer to one canonical customer, following BR05.
- **R06 (P1)** — Validate every record against the business rules. Records that fail go to quarantine with a reason code and never reach the revenue figures. If a record that was valid becomes invalid, its previous version leaves the figures.
  Rationale: The last sentence closes a fail-open gap: without it, an invoice that starts failing would leave its old version in the dashboard totals.
- **R07 (P1)** — Processing is idempotent: the same record received any number of times, from any path, is stored once.
- **R08 (P1 figures, P2 trend labels)** — Dashboard: total monthly revenue and monthly revenue per customer, filterable by source, customer and date range, with each customer's trend (BR08).
- **R09 (P1)** — Quarantine view: every rejected record with its source, source document reference, reason code and rejection date.
- **R10 (P1)** — Freshness: per source, the dashboard shows when the last successful sync finished. For Source B it also shows the export date of the latest file, taken from its file name.
  Rationale: A CSV has two dates, when it was exported and when it was ingested; an old file ingested today is not fresh data.
- **R11 (P2)** — Access control as described in "Users and access".
- **R12 (P2)** — Traceability: any monthly revenue figure can be expanded into the list of source documents that make it up.
- **R13 (P1)** — A message that fails 5 times (Q4) moves to a dead-letter queue and is reported, instead of being retried forever. If an older valid version of that record is in the figures, it leaves them and the record is quarantined with reason `PROCESSING_FAILED`.
  Rationale: Fail-closed (constitution principle 1): if the new version could not be processed, the old one can't be assumed still valid, so it leaves the figures and shows in quarantine rather than risk a wrong value on a board deck.
- **R14 (P1)** — Reconciliation: a check compares, per month, the stored revenue for Source A against totals computed directly from ERPNext, and reports any difference.
  Rationale: Reconciliation is the month-end proof that the dashboard matches the ERP, including anything webhooks and polling missed; incremental sync can drift, and this check catches drift in the system rather than leaving it to the CFO.
- **R15 (P1)** — When the customer mapping changes, records in quarantine with reason `UNKNOWN_CUSTOMER` are validated again.
  Rationale: Without this, mapping a new customer would release nothing from quarantine.
- **R16 (P2)** — Readability: revenue is the most prominent information wherever it appears (chart, tooltip, table), and every text on the dashboard, revenue values first, has a color that contrasts with its background in both light and dark mode, so no figure is ever dark-on-dark or light-on-light. The same holds for the controls people use to read the data: filter fields, their icons (such as the date-picker calendar) and dropdown arrows.
  Rationale: People come to the dashboard for revenue, so it must be the first number the eye finds in any theme (in dark mode the tooltip value once rendered near-black on a dark background); the how (color tokens, 4.5:1 contrast) is in the PLAN.
- **R17 (P2)** — Responsiveness: on a warm deployment, moving between the dashboard pages, applying a filter and expanding a monthly figure into its source documents (R12) each show the data within one second (AC22), with up to 1,000 invoices across both sources (this lab holds about 300). Speed never comes from serving stale data or from weakening access: every figure and every sync-health signal is read from the database on each request, so after a sync commits, the next load shows the new figures and the new "last successful sync" (R10); and access control (R11) keeps its current strength, including signing out and removal from the allowlist taking effect on the next request. A failure is never hidden as fast empty data. Cold start is Q9.
  Rationale: Measured with Chrome DevTools, production took 0.7–1.3 s per screen warm and 5.8 s on cold start, and the cause was neither volume (~285 invoices) nor ERPNext, since the dashboard reads only Postgres; the diagnosis and fix are in the PLAN.
- **R18 (P2)** — Feedback while loading: the dashboard always shows that it is working. A click on the navigation, a filter or a monthly figure gets an immediate visible response; while data loads, the page keeps its layout with placeholders that hold no figures; when a filter is applied or a figure is expanded, the figures it replaces leave the screen at once and placeholders take their place, so no figure is ever on screen that is not the current result; and a failed load says what failed and offers to try again. A page with any failed load is in error, never in a degraded state that looks like data. The filter row keeps its fields aligned and its actions together at any screen width (AC31).
  Rationale: Speed (R17) and perceived speed (R18) differ: even when fast, a click with no response looks broken. Skeletons replace dimmed old tables because a dimmed number is still readable and can end up in a board-deck screenshot, which would break fail-closed.
- **R19 (P2)** — Source breakdown on the monthly chart: each month's revenue bar shows how much came from each source, while the month's total stays the leading figure. A source with negative revenue in a month (credit notes, BR07) is drawn below the zero line, so the bar still reads as signed parts; the month's total is always the tooltip's leading figure and the table's figure. The sources are named as in the Customers filter ("ERPNext (Unit A)", "Unit B export"). The table below the chart keeps only the total per month.
  Rationale: The chart answers "how are we doing" first and "where does it come from" second: stacked bars keep the consolidated total as the bar height, the board-deck number, while colors split it by source.
- **R20 (P2)** — Financial clarity between Sync health and Revenue: a finance member can tell, from the screen alone, which sources make up each figure. The reconciliation (R14) is presented as what it is, a check of ERPNext (Unit A) against the ERPNext records we stored, never as a check of both units; its period is the validation period (BR03, January–December 2026). Sync health also shows a source breakdown of valid revenue — ERPNext (Unit A), Unit B export and their sum — for the reconciliation's period (Q10). The breakdown's ERPNext figure is valid revenue and is comparable only with the reconciliation's stored total; the reconciliation's ERPNext total also counts ERPNext documents that are in transit, in quarantine or dead-lettered, and the screen says so. Every figure states its period (first and last month; when the period includes the partial month, it runs through the as-of date and is marked partial). Figures from different periods, or a reconciliation whose stored total no longer equals the current ERPNext figure for its period, are never shown as if they were directly comparable. Missing or failed data is never shown as zero. The Revenue page shows total revenue, ERPNext (Unit A) and Unit B export for its own period (Q10). Whether the breakdown is comparable with the reconciliation is a business rule, decided in a service and unit-tested.
  Rationale: Sync health showed an ERPNext total of $462,664.00 and Revenue $572,579.83; the $109,915.83 difference is exactly Unit B's valid revenue for the same months, so the gap is a labeling problem, not an error, and the reconciliation stays Unit A only (R14).
- **R21 (P2)** — Customer trends at a glance: on the Customers page the trend of every customer is always visible; on desktop screens at least 1,440 CSS px wide (100% zoom) the whole table fits; on narrower screens or longer month ranges, the customer, total and trend stay in view while only the months scroll, and it is obvious that more months exist and how to reach them with mouse, trackpad, touch and keyboard. Every monthly figure stays complete (dollars and cents) and readable, and a trend is never told by color alone.
  Rationale: The 13-column Customers table overflows the page's 1,100 px width, pushing the Trend column, the decision figure of the screen, out of view, with the sideways scrollbar at the bottom of the table.

## Business rules

Each invalid invoice gets exactly one reason code: the first rule that fails, checked in this order: BR03 (required fields and dates), BR04 (currency), BR06 (conflicting rows), BR02 (totals), BR05 (customer).

Rationale: The order gives every rejected invoice exactly one reason, the first rule it breaks (otherwise UB-26005 would get both CONFLICTING_DUPLICATE and TOTAL_MISMATCH, and UB-26023, with a blank customer, both MISSING_FIELD and UNKNOWN_CUSTOMER), so the quarantine says what to fix first.

- **BR01 — Only final invoices count.** From Source A, only submitted invoices count. Drafts are ignored. A cancelled invoice is removed from the figures. When an invoice is amended, ERPNext cancels the original and creates a new document linked to it (`amended_from`); the new document counts once it is submitted.
  Rationale: In ERPNext, docstatus 0 = draft, 1 = submitted, 2 = cancelled; an amendment starts as a draft (e.g. ACC-SINV-2026-00012-1) and counts only once submitted, otherwise it would count twice. ERPNext won't delete a submitted invoice, but cancel-then-delete between two polls removes the document before the cancellation is seen, so the sync also reads ERPNext's deleted-documents log (EC12).
- **BR02 — Totals must add up.** An invoice's net total must equal the sum of its lines' net amounts, within USD 0.01. For Source B, the line amount is quantity times unit price. Otherwise: quarantine, reason `TOTAL_MISMATCH`.
  Rationale: The one-cent tolerance absorbs rounding; ERPNext already guarantees it, and the legacy system is where totals break.
- **BR03 — Required fields and dates.** Customer, invoice date, currency and at least one line are required; missing any: quarantine, reason `MISSING_FIELD`. A Source B row without `INV_NO` can't be grouped into an invoice; it is quarantined on its own, with reason `MISSING_FIELD` (Q8). Each source has one fixed date format (Source A: ISO `YYYY-MM-DD`; Source B: `MM/DD/YYYY`). A date that doesn't match its source's format, or falls outside January–December 2026, goes to quarantine with reason `INVALID_DATE`.
  Rationale: A fixed format per source avoids the ambiguity of 03/04/2026 (April 3 in the US, March 4 in Brazil).
- **BR04 — USD only.** Every record carries a currency (Source B has a `CURRENCY` column). Any currency other than USD: quarantine, reason `UNSUPPORTED_CURRENCY`.
  Rationale: Converting currency requires agreeing on a rate source and date; showing a record as unsupported is safer than converting it with an FX rate nobody agreed on.
- **BR05 — Customer resolution is explicit.** Every canonical customer is listed in the customer mapping, including customers that appear in only one source. Source A customers are resolved by their ERPNext customer ID. Source B names are normalized (case, punctuation, extra spaces) and looked up in the mapping; normalization only proposes a match, the mapping decides. Legal suffixes such as Inc, LLC or Co are never stripped automatically. A name that is not in the mapping goes to quarantine with reason `UNKNOWN_CUSTOMER`.
  Rationale: Stripping suffixes automatically would merge "Acme Co" and "Acme Inc", two different companies, into one line on the board deck; normalization only suggests, the versioned mapping decides, and Source A uses the customer ID, which doesn't change if someone edits the name.
- **BR06 — Duplicates in an export.** The export has one row per invoice line. Within one file, when two rows have all normalized columns identical (same hash), `INV_TOTAL` decides: if it matches the sum with the repeated row counted once, the repeat is an export duplicate and is dropped; if it matches the sum with both rows, both are real lines and are kept; otherwise BR02 applies. Within one file, rows with the same invoice number that disagree on an invoice-level column (customer, date, total or currency) put the invoice in quarantine with reason `CONFLICTING_DUPLICATE`. Across files, BR10 applies.
  Rationale: Lines of one invoice differ on purpose; a conflict exists only when rows disagree on invoice-level data. An identical repeated row may be an export glitch or two real identical lines, so the invoice total arbitrates instead of guessing, and nothing disappears silently, which would be fail-open.
- **BR07 — How revenue is counted.** Monthly revenue is the sum of the net totals (after discounts, before tax) of valid invoices, grouped by the calendar month of the invoice date. Credit notes (ERPNext returns, `is_return`) count as negative revenue in the month of their own invoice date.
  Rationale: Tax is government money, not revenue, and a credit note counts in its own month, not the original invoice's, as accounting does. Amounts keep the sign from the source and no rule validates the sign (e.g. a positive credit note), a known limitation because the seed has no returns.
- **BR08 — Trend.** A customer's trend uses its monthly revenue from both sources combined (BR07).
  - **As-of date:** the earlier of (a) the date of Source A's last successful sync and (b) the export date of the newest Source B file.
  - **Complete month:** a calendar month whose last day is before the as-of date.
  - **Has revenue in a month:** the customer's net revenue in that month is greater than zero.
  - **Last 3 / previous 3:** the last 3 complete months, and the 3 complete months before them. **Last 2:** the last 2 complete months.

  Rules are applied in this order; the first that matches wins:
  1. **churned** — has revenue in some complete month before the last 2, and no revenue in the last 2;
  2. **new** — the customer's first month with revenue in the stored data is one of the last 3;
  3. if revenue in the previous 3 is zero or less: **growing** when revenue in the last 3 is greater than zero, otherwise **stable**;
  4. **growing** — last 3 > previous 3 × 1.15;
  5. **declining** — last 3 < previous 3 × 0.85;
  6. **stable** — anything else.

  Amounts are compared exactly, in cents, with no rounding. (Thresholds decided in Q2.)
  Rationale: Growth is written as a formula (× 1.15, × 0.85) with an explicit branch for a zero or negative base, since "15% above" has two readings that diverge there; only complete months count, otherwise everyone looks like they're declining mid-month, and churned/new look at the whole stored history so a customer who stopped buying in March doesn't show as new. Known, accepted false positives: a single July purchase or a quarterly buyer with an empty August–September shows as churned, history starts in January 2026, and Sunset Grill sits at −16.08%, only $144.58 from the threshold, so any test that changes its invoices flips it to stable.
- **BR09 — Read-only toward sources.** This version never writes to any source system. The constitution allows draft write-backs with approval; this version deliberately uses only the read side.
- **BR10 — Each Source B export is a full snapshot.** A file contains every invoice from 2026-01-01 up to its export date. The newest file is the one with the latest export date in its file name; a file older than the newest one already ingested is rejected as a whole. An invoice present in an earlier file but missing from the newest one leaves the figures, and any open quarantine entry for it is closed.
  Rationale: "Newest" means the export date in the name, not upload order, so a late, stale file can't delete or resurrect invoices; a vanished invoice's quarantine entry is closed because there is nothing left to fix, and since the newest file is the truth for Unit B, Source B needs no reconciliation.

## Edge cases

- **EC01** — An invoice is cancelled and amended in Source A after it was synced: the original leaves the figures; the amended document counts once it is submitted (BR01).
- **EC02** — The same invoice arrives by webhook and by periodic fetch: stored once (R07).
- **EC03** — Several invoices share the same last-modified timestamp across a page boundary: none is skipped and none is double-counted (R01).
- **EC04** — Processing stops in the middle of a batch: unprocessed records are retried and no record is stored twice.
- **EC05** — Source A is down or rate-limits: the sync retries with backoff, and "last successful sync" does not move forward until a run succeeds.
- **EC06** — The same export file is ingested twice: nothing is duplicated.
- **EC07** — An export file has the wrong columns or is empty: the whole file is rejected with a clear reason and nothing from it is ingested.
- **EC08** — A record quarantined for bad data is fixed at the source and synced again (Source A) or re-exported in a newer file (Source B): it leaves quarantine and enters the figures.
- **EC09** — A record quarantined as `UNKNOWN_CUSTOMER` is resolved when its customer is added to the mapping (R15).
- **EC10** — A valid invoice is updated at the source and now fails validation: it moves to quarantine and its previous version leaves the figures (R06).
- **EC11** — An invoice for a past month arrives late: that month's figures change, and that source's last-sync time is the run that brought it.
- **EC12** — An invoice is cancelled and then deleted in Source A between two sync runs: it still leaves the figures.

Rationale: EC03 is the classic date-pagination trap, which is why the cursor is (modified, name); EC05 is why the cursor advances only after commit; EC10 is the fail-open gap closed by R06.

## Out of scope

- Writing anything back to source systems, including drafts.
- Purchase invoices and cost analysis (the client's second question). Planned extension.
- Taxes as a separate figure (decided in Q1).
- Currency conversion.
- Fuzzy or AI-based customer matching. No LLM in this version.
- Editing, deleting or annotating data in the dashboard.
- Uploading export files through the dashboard.
- More than two sources, multiple companies or multiple tenants.
- Real-time figures. Updated within minutes is enough.
- Payments, receivables, collections and forecasting.
- Exporting data or generating board decks automatically.
- Webhook secret rotation.
- Reconciliation for Source B: the newest file replaces all Source B data (BR10), so there is nothing to reconcile.

Rationale: This list keeps the build from growing beyond what was asked; if an item here appears in the plan, the plan is wrong. Costs are the obvious next step, and the design already supports them as one more document type through the same adapters.

## Acceptance criteria

Rationale: Each criterion states how to trigger the situation and what to measure, so the result is pass or fail without interpretation; the parentheses name what it proves.

- **AC01** (R01, R07) — Given a completed sync, when the sync runs again with no changes in either source, then the count of stored invoices and every monthly total are exactly the same.
- **AC02** (R01, BR01, EC01) — Given a completed sync, when one invoice is cancelled and amended in ERPNext and the amendment is submitted, then the next run's log lists only those two documents as fetched (plus anything in the overlap window), the cancelled one leaves the figures and the amended one counts once.
- **AC03** (R07, EC04) — Given a batch in progress, when a test switch makes processing throw after the 3rd message, then after the visibility timeout every invoice from that batch is stored exactly once.
- **AC04** (R06, R09, BR02–BR06) — Given the Source B export with planted errors, when it is ingested, then each planted error listed in `data/legacy_unit_b.README.md` appears in quarantine with its expected reason code, source, document reference and rejection date, and none of them is counted in the figures.
- **AC05** (R14) — Given Source A synced, when the reconciliation check runs, then it reports no unexplained difference: every invoice whose stored value differs from ERPNext is accounted for as in transit, in quarantine or in the dead-letter queue.
  Rationale: An ERPNext invoice in quarantine is correct behavior, not an error, so it must not fail reconciliation; the per-customer check across both sources is AC18, because reconciliation (R14) covers Source A only.
- **AC06** (BR01) — Given drafts in ERPNext, then none of them is counted.
- **AC07** (BR08) — Given the seeded data from both sources and an as-of date fixed at 2026-10-16 for the test, then every customer's trend matches the expected trend listed in `scripts/seed/README.md`.
  Rationale: The trend depends on the date (from November, October becomes a complete month), so the test fixes it; with 2026-10-16 the last 3 complete months are July–September and the previous 3 April–June, while the live dashboard uses the last sync date.
- **AC08** (R02) — Given a change in ERPNext, when ERPNext sends its webhook, then the change appears in the figures within 2 minutes. When the webhook is disabled in ERPNext, the change still appears within 6 minutes (the 5-minute fetch interval from Q3, plus 1 minute).
- **AC09** (R02) — Given a webhook request with a missing or invalid signature, then it is rejected (HTTP 401) and nothing is queued.
- **AC10** (R11) — Given a Google account that is not on the allowlist, then it sees the access-denied page and no data. Given an allowlisted account, then it can view and filter; every non-GET data route returns 403 or 405 (both in the constitution), and the database rejects inserts, updates and deletes from signed-in users.
- **AC11** (R10, EC05) — Given the ERPNext URL pointed at a stub that returns HTTP 502, when a sync runs, then "last successful sync" still shows the previous successful run, and after the URL is restored the next run succeeds and updates it.
- **AC12** (R12) — Given any monthly figure for a customer, when it is expanded, then it lists source documents whose net totals add up to that figure.
- **AC13** (R13) — Given a message that fails every attempt, then after 5 attempts (Q4) it is in the dead-letter queue and no longer retried.
- **AC14** (EC06, EC07) — Given an export file already ingested, when it is uploaded again, then nothing changes; given a file with wrong columns or no rows, then it is rejected as a whole and nothing from it is stored.
- **AC15** (R15, EC09) — Given a record in quarantine as `UNKNOWN_CUSTOMER`, when its customer is added to the mapping, then it leaves quarantine and enters the figures.
- **AC16** (R06, EC10) — Given a valid invoice in the figures, when its source data changes so that it fails validation, then it appears in quarantine and its old amount leaves the figures.
- **AC17** (BR10) — Given an invoice present in an earlier Source B file, when a newer file without it is ingested, then it leaves the figures and any open quarantine entry for it is closed. Given a file older than the newest one already ingested, then it is rejected as a whole.
- **AC18** (R04, R05, R08) — Given both sources synced, then each customer's revenue in the dashboard equals the sum of that customer's valid Source A invoices plus valid Source B invoices, checked with a query over the canonical tables.
- **AC19** (BR06) — Given an invoice whose identical repeated row is an export duplicate (its `INV_TOTAL` matches with the row counted once), then it counts once and is not quarantined; given one whose `INV_TOTAL` matches only with both rows, then both rows count.
- **AC20** (R16) — Given the monthly revenue chart in light or dark mode, when a month is hovered, then the tooltip shows that month's revenue as its most prominent element (larger and bolder than the month and the invoice count), and every text in it has a contrast of at least 4.5:1 against its background.
- **AC21** (R16) — Given the Customers filters in dark mode, then the From/To date-picker icons, the dropdown arrow and the field text are light on the dark field, clearly visible; in light mode they are dark on the light field.
- **AC22** (R17) — Given an allowlisted user signed in on production, browser cache enabled, no throttling, measured from the owner's machine in Brazil on its usual connection, and a warm deployment (the same page requested within the previous 5 minutes), when they move from any dashboard page to Revenue, Customers, Quarantine or Sync health through the navigation, apply one Customers filter change (source or date range), or expand a Customers month figure into its documents, then every data element of the target (all figures, tables and the "data as of"/freshness line, or its empty state) is on screen within 1 second of the click. Time runs from the click to the last data response being rendered, recorded with Chrome DevTools; each flow passes on its own as the median of 3 consecutive runs; a run with a failed or retried request is discarded and repeated.
- **AC23** (R17) — Given the local development server with every page and data route already visited once (compiled), when the AC22 flows run on it, then each one's data is visible within 1.5 seconds, measured and aggregated as in AC22.
- **AC24** (R17, R11) — Given the faster dashboard, then AC10 still holds: an account off the allowlist gets 403 Problem Details from every data route and the access-denied page; an anonymous call (no session, or an expired or tampered token) gets 401; no data request returns rows to any of them.
